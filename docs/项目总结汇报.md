# 《去狸的岛》项目总结汇报

**汇报日期**：2026年8月  
**项目名称**：《去狸的岛》（对内工程名：河可松）  
**项目性质**：十日完整可通关叙事游戏（非演示版、非序章）  
**技术形态**：Godot 4.7 俯视像素；可运行于 Windows 与 Web  
**核心表述**：在一部写死的十日剧情里，放进一个真会聊天的人。

---

## 一、项目概述

本项目是一部以河边小农场为舞台的叙事游戏。玩家独自守着一处院子。雨夜里，狐狸「小狸」前来求收留。此后十个游戏日内，玩家与她共同过日子：种萝卜、说话、把不想忘掉的事写进本子。第五天须决定继续收留或将其赶走，并据此走向不同结局。

种田在本项目中定位为生活质感，而非经营扩张。可种植的田块仅限围栏内三垄；场景为单张院子，不设第二张地图、不设第二名角色。对外只称「第几天」，不向玩家使用「第几周」「三十五日」等旧口径。

作品在结构上分为必须分开表述的两层。第一层是剧情：今日发生何事、主节点如何推进、去留如何分叉、结局如何收束，均由策划定稿与节点文案规定，不因模型临场发挥而改写。第二层是角色：小狸如何开口、是否答应浇田并走到田边、本子上留下哪几页，由玩家输入与对话模型共同完成，但记忆内容受白名单约束。两层的权限一旦混淆，便会出现「模型改写了今天的故事」或「角色只会聊天、进不了院子」两类失败。

须特别说明：小狸会周期性遗忘、第四天将玩家视为陌生人、第十天叙事收网等，属于本作品的剧情设定，用以完成「被记住—被忘记—被认回」的情感弧线。上述内容是故事要讲的事，不应表述为本项目的机制创新或技术突破。

在联网条件下，小狸的对话可走云端大模型；在断网或接口不可用时，游戏仍提供完整固定剧本与本地兜底台词，保证十日流程可以走完。因此本项目的交付标准是「可通关的完整故事」，而不是「仅在模型可用时才能推进的聊天演示」。

## 二、工作目标与完成情况

本项目的内容目标可概括为三项：十日结构完整可通关；个性化可被玩家感知；叙事在终章闭合。对照任务清单，日历骨架、主节点文案、去留分叉、四结局（含第五天赶走后的提前收束）、记忆本子系统、对话与农事联动等主体工作已经落地。标题与关于界面已按「十日完整故事」统一对外名称。Web 端具备可试玩地址；Windows 可执行文件已经导出，尚待开包冒烟确认。

对话与记忆方面，已经实现如下约束：大模型不得改写主线，不得自行写入长期记忆；失忆日不向模型提供情节性旧事，从而使剧情中的遗忘与系统中的记忆关闭相一致；本子具有页数上限，支持钉页与写满后当面划掉；玩家口头委托浇水、种植、收获或「过来」「去树洞」时，角色应走到相应地点并执行，而不是仅在对话框中表态。

个性化方面，策划要求「认真聊天、完成约定」与「几乎不聊天、只种田速过」两条路径，在第七日称名与约定、终章回声等处必须能够区分。相关槽位与节点变体已经接线；三档亲密度（远、近、贴）的肉眼验收仍待专门走查。

尚未收口的工作主要有三类。第一，收留线与赶走线各需一条完整的人工通关记录，以确认无阻断性缺陷。第二，亲密度三档在第二、七、八日的观感差异尚需人工核对。第三，对外发布页与安装包冒烟测试尚未作为发布里程碑勾选完成。自动化测试中另有六条与十日主路径无关的既有失败项，本阶段明确不纳入修复范围。

## 三、创新点

本项目的创新不在「使用了人工智能」，也不在「讲述了遗忘」。行业内以大模型驱动角色对话的尝试并不少见，其常见问题是把编剧权交给模型，导致主线发虚、通关条件不稳定。本项目采取相反的产品立场：**以完整、可通关的剧情游戏为本体，在其中嵌入一名能够自然语言交流的同伴，同时严格限制模型不得担任编剧。**

据此形成四项可陈述的创新。

第一，权限三分。剧本层决定「今天发生了什么」；记忆层（本子）决定「她被允许记得什么」；模型层只决定「这句话怎么说」。主动开口若与当日叙事相关，必须携带当日剧情上下文，与节点变体、亲密度档位保持同一口径。信纸等已写正文以策划表为准，模型只作铺垫，不得另撰与当日节点矛盾的台词。

第二，记忆被做成玩家可操作、且有代价的界面，而不是后台不可见的聊天日志。本子页数有限，玩家可以翻阅、指定留下（钉页）；写满时须当面划掉一页。模型引用「以前的事」时，只能引用本子上存在的条目，并经校验拦截无根据的编造。由此，「让她记住我」成为有取舍的选择，同时也构成对模型幻觉的结构限制。

第三，话语进入场景。玩家委托浇田、收菜、去商店，角色须先移动至目标再执行；玩家说「过来」「去廊下」「去树洞」，或角色自己说出相应承诺，亦应产生走位。农事指令与身体走位分轨处理，避免与「去商店买种子」等已有委托冲突。口头答应却不执行，会被视为体验失败。

第四，个性化设有验收标准，而不是「接上模型即算完成」。若两条游玩路径在关键日听不出差别，则个性化视为未交付。该标准把「AI 角色」从技术展示拉回到策划可验收的产品指标。

以上四点共同回答一个问题：如何让「写死的十日」与「真会聊天的人」共存，而又不互相破坏。遗忘作为剧情刀法，在系统上得到支持（失忆日关闭情节记忆），但其本身不是创新表述的主语。

## 四、主要难点

本项目的困难，集中在「活的对话」与「死的结构」必须同时成立。

其一，模型与剧本争夺解释权。一旦主动搭话交给模型，就容易出现念错当日节点、在失忆日呼唤玩家姓名、把第四天说成久别重逢等情况。若为求稳而全部改回固定台词，则「真会聊天」名不副实；若放任模型即兴，则十日主线失去权威。解决办法只能是联调：凡与当日叙事相关的开口，必须带齐剧情上下文；客户端禁止另写与节点、档位矛盾的台词；节点变体或邀请语气若有修改，本地服务与云端镜像必须同步后重新部署。

其二，模型倾向于把长对话当成事实记忆。多轮之后，它会陈述本子上并不存在的约定，或把寒暄说成共同经历。若仅在提示词中要求「不要编造」，约束并不稳定。必须把本子当作白名单，在输出侧校验引用，并在失忆日从源头停止投喂情节记忆。换言之，剧情要求她忘记，系统就必须在当轮不提供可引用的旧事，而不是要求模型「表演遗忘」。

其三，语言与身体容易脱节。玩家会自然地认为：既然可以说话，说「去浇田」就应当看到她走向田垄。若对话系统与农事、移动系统分离，就会出现「嘴上答应、人仍站在廊下」的失信。农事须走意图解析与执行编排，走位须走单独的动作白名单，并在角色忙碌、信纸或商店打开时丢弃冲突动作。

其四，产品形态曾经历从三十五日、五周结构到十日完整故事的收缩。日历上限、每日节点、结局阈值、觉醒日、对外文案均须改口。若残留「第五周」话术，或将终章额外碎片计入 True 结局条件，就会出现策划与实现不一致。收缩过程中的难点不在删天数，而在所有依赖旧日历的系统都要重标定。

其五，对话服务存在本地与云端两套实现。只修改其中一端，会出现编辑器内表现正确、线上玩家仍读到旧提示词的情况。该问题属于工程纪律，但会直接破坏策划口径，故必须列入难点，而非视为单纯运维细节。

## 五、突破与阶段性成果

针对上述难点，项目形成如下突破。

在叙事与系统对齐方面，第四天进入陌生化后，系统关闭情节性可引用记忆，并对「又见面了」一类越界称呼与回忆进行拦截。剧情中的「她不认得你」因此能够落地为可玩状态，而不是一段无法核对的旁白。

在记忆方面，本子由剧情道具提升为玩家接口：可见、可钉、写满须划。防幻觉与情感选择使用同一套规则，避免再为「模型乱说话」另做一套不可见的后台过滤而玩家毫无感知。

在话语与世界方面，浇种收等农事沿既有委托链路执行；「过来」「去地点」等身体指令单独白名单化，并覆盖角色自己说出的前往承诺。聊天记录对人显示自然语言，对模型回放结构化契约，以降低多轮对话后格式漂移、人设走样的概率。

在交付可靠性方面，接口不可用时的本地兜底覆盖十日主流程，使通关不取决于模型是否在线。对玩家而言，这意味着故事可以结束；对项目而言，这意味着「完整游戏」与「AI 演示」被区分开来。

内容侧，十日主节点、去留分叉、四结局与觉醒收束已经可运行；AI 伙伴长线（引用可见、本子操作、人设纪律、玩家侧本子暗线等）已经按阶段接入。Web 与 Windows 导出链路已经打通，具备演示与内测条件。

## 六、主要问题与处理原则

实施过程中遇到的问题，本质上不是零散缺陷，而是「写定剧情」与「生成式角色」叠加后必然出现的几类矛盾。处理上采取原则约束，而非逐条修补话术。

**第一，剧情意图与玩家理解不一致。**  
中段失忆是叙事设计，但玩家可能将其理解为存档或程序错误。处理原则是：在体验入口用叙事而非系统口吻完成预期管理；同时让系统状态与剧情一致（失忆日不提供可引用的旧事、拦截越界称名与亲昵回忆），使「她不认得你」可被玩到、可被解释。该问题在设计上已闭合，仍须通过完整通关手测确认是否还会被误读。

**第二，生成式对话越权。**  
模型会改写当日事实、编造本子上不存在的经历，或把尚未 unlock 的叙事提前说出口。仅靠提示词约束不稳定。处理原则是权限前移：剧本与记忆为权威，模型只生成「如何说」；引用必须落在白名单内；与当日节点相关的开口必须携带剧情上下文。经实测，写入本子的内容召回较为稳定，未写入的口头信息召回仍不稳定，作为已知风险保留。

**第三，言语与世界状态脱节。**  
玩家默认「说了就会发生」。若对话与场景执行分离，角色便失去可信度。处理原则是把委托、口头承诺与空间移动纳入同一验收：答应的农事必须执行，承诺的走位必须发生，并在角色忙碌或叙事面板占用时明确丢弃冲突动作。该闭环已经建立，边界情形仍待通关手测覆盖。

**第四，多端交付与口径一致性。**  
同一套玩法需在编辑器、Web、Windows 及云端对话服务上表现一致。本地通过、线上仍为旧逻辑，或某一端操作失效，都会使「可交给他人试玩」不能成立。处理原则是：对话规则双端同步后部署再验收；输入与界面按设备形态适配；不以单一环境通过代替发布验收。

**第五，产品收缩后的结构重标定。**  
由长周期结构收束为十日完整故事后，日历、文案、结局条件与对外表述必须同步改口，否则策划与实现会继续引用两套时间尺度。处理原则是对外统一为十日口径，结局条件按十日规则重计，终章附加揭示不倒计为通关门槛。

以上五类问题，前三类属于本项目的产品命题，后两类属于把命题做成可交付物时的工程与范围命题。零散的视听、控件与文案修补从属于后两类，此处不展开。

## 七、工作方法说明

本项目在程序实现上较多使用生成式辅助工具。书面汇报中需要界定责任边界：工具用于加速实现，不构成项目成果本身。应由项目负责人承担并能够答辩的部分包括：十日结构与去留规则如何规定；剧本、记忆与对话三者的权限如何划分；何谓「做完」（可通关、关键日可区分、言出必行）；以及实际游玩是否符合上述规定。生成结果若违反上述规定，即予修改或废弃。

不将「使用人工智能编写代码」列为创新点或业绩表述。

## 八、存在的不足与下一步

当前最大的不足，是完整人工通关记录尚未作为里程碑关闭。系统具备通关结构，不等于已经完成收留线与赶走线的无阻断确认。亲密度分档目前已接线，观感差异尚需在关键日人工核对。安装包与 Web 发布仍处于「可运行」与「可正式交付」之间。生成式角色对未写入本子的信息召回不稳定，后续若加强，须以不破坏失忆日纪律为前提。

下一步建议按此顺序推进，不扩大玩法范围：第一，收留线与赶走线各完整走通一次，记录阻断并修复；第二，按远、近、贴三档核验第二、七、八日的台词与邀请差异；第三，完成 Windows 开包冒烟，并固定 Web 试玩地址与对外简介。明确不做的事项包括：第二张地图、第二名角色、新作物种类，以及将日终日记由「概括」改成「取舍压缩」的方案。

## 九、结语

《去狸的岛》要交付的，不是一段可以无限聊下去的角色，而是十天之内能够开始、能够选择、能够结束的故事；同时，故事里的那个人必须真正能够被交谈，并且谈过的话能够进入田里、进入本子，而不是停在对话框里。

本项目认为可以成立的产品位置是：以写定的十日剧情为骨架，以受约束的对话角色为血肉。骨架保证通关与口径，血肉保证每一次游玩仍因玩家怎么说话而不同。遗忘是这条故事选择的刀法；创新在于刀法落下时，聊天的人仍在场，且没有把剧本抢走。

对外介绍可采用如下书面表述：

> 《去狸的岛》是一部十日完整剧情游戏。玩家在河边农场与一只狐狸共同度过十天。主线、选择与结局均由剧本规定，通关并不依赖于对话模型是否在线。狐狸可以自然语言交流，能够按玩家的委托去浇田、走近或前往院中地点，也可以把想记住的事写入页数有限的本子。她会记住玩家，也会在故事中途将玩家视为陌生人。模型只负责「如何说话」，不负责「今天发生什么」。
